# F4 数秘術の確定結果アダプター

## 実装

`src/numerology-confirmed-result.js` で、計算チェックポイントと外部から供給される承認レコードを照合し、既存の `numeria-confirmed-divination-result.v1` へ変換する。UIは現在の鑑定スナップショットと `window.NumeriaNumerologyResultApproval` をアダプターへ渡す。旧共通global内の数秘結果を無条件には参照しない。他占術の既存経路は保持する。

承認レコードの形式は `numeria-numerology-result-approval.v1`。以下を全て確認する。

- 保存されたSession ID、数秘術、既知のチェックポイント／計算版、入力済みの日付。
- チェックポイント全体が現在の入力から再計算した値と一致すること。
- 承認対象のSession、本人／相手、使用氏名と出生時／現在の種別、相性オプション、関係種別、基準日、計算版が一致すること。
- 承認対象のコア数と全14ページの値・不足状態が一致すること。
- 承認記録のID、確認者、日時、対象結果の独立検証がcompleteであること、および空でない証拠参照。
- サンプル承認・サンプル結果を拒否すること。部分照合レポートや計算済みチェックポイントを承認レコードへ自動昇格しない。

結果の不一致、版違い、入力不足、未承認は理由付きで拒否する。キー順の違いだけで不一致にはしない。結果ブロックも氏名変更時に更新し、以前の承認数値を画面に残さない。印刷時も現在の鑑定と再照合する。

## 承認供給の境界

このアダプターは承認の対象・内容を検査する変換層であり、承認の発行元認証や改ざん防止の境界ではない。信頼できる発行元から取得・認証した承認を呼出側が渡すことが前提。現在は承認レコードを発行するAPI・署名検証・承認ボタン・保存経路を実装していない。globalは将来の供給口であり、現行データが自動承認されることはない。ブラウザ上の値だけをサーバーの権限判断に用いない。

実在の本番承認レコードは今回作成しない。肯定経路の承認は検証スクリプト内だけのfixture。前回の数値照合11例はpartialのままで、各鑑定のcompleteな独立検証証拠として流用しない。

## ページの発行条件

計算結果を確定形式に変換できても、14ページの `pageAvailability` は全てfalse。必要入力不足、ピークの日付境界未解決、登録解説・正式図表未接続を区別する。ページ固有の承認証拠は生成しない。したがって計算承認だけで固定ページの正式発行を開放しない。

## 検証

実チェックポイントとfixture承認からの変換、人物／基準日／版／氏名／相手／相性の変更、保存数値の改変、承認数値の改変、証拠不足、partial、サンプル、循環値、入力不足、ピーク境界、旧global結果の遮断を検査する。実ランタイムの結果ソース選択・数秘結果ブロック更新もVMで実行。14固定ページが引き続き発行を止めることを確認する。
